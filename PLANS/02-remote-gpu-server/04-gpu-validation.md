# 02.04 — GPU validation

- **Objective:** Prove each selected policy performs real RTX 3090 inference rather than merely starting.
- **Inputs/prerequisites:** Ready server; WSL-local OpenPI client; verified available outer process-deadline tool (normally GNU `timeout`); GPU metrics access.
- **Implementation tasks:** Capture sanitized `nvidia-smi` baseline; run every pre-phase-03 WSL-local smoke invocation under a validated finite outer process deadline with TERM then bounded KILL fallback and record timeout exits, so the stock client cannot hang phase 02; time request 1 as cold, then issue two warmups and measured warmed inferences per profile; validate handshake identity, backend/device, response dtype, and finite `(50,14)` actions; capture process GPU memory/utilization before/during; record cold/warm latency and checkpoint/profile/SHA; detect CPU fallback and fail. Preserve the direct converter's full-FP32 default and the JAX runtime. Project orchestration defaults to `auto`: read Linux `MemAvailable` once, select bounded `partial-bfloat16` below 16 GiB and full FP32 otherwise, allow only explicit enumerated overrides, and record the selection. The partial mode from [`LOW_MEMORY_CONVERSION_OPTIONS.md`](LOW_MEMORY_CONVERSION_OPTIONS.md) proves one BF16 leaf against FP32→BF16, consumes every stored source leaf exactly once, copies each mapped target once into a GPU-resident model, releases each source leaf, saves standard 1 GB shards into an owned temporary directory, copies the checkpoint's own assets, strict-loads with only the proven tied alias, and publishes atomically. Add explicit `OPENPI_POLICY_BACKEND=jax|pytorch` selection: JAX uses the pinned original checkpoint; PyTorch requires the profile-matched local converted directory, rejects missing/mismatched artifacts without fallback, disables optional `torch.compile` autotuning for the memory-bounded demo, omits JAX-only gates, verifies Torch CUDA/RTX placement, and reports backend/device metadata. Phase 03 replaces the coarse inference guard with per-stage client deadlines/close.
- **Files expected to change:** `examples/convert_jax_model_to_pytorch.py`, `src/openpi/policies/policy_config.py`, `src/openpi/models/model.py`, `scripts/convert_policy_checkpoint.sh`, `scripts/start_policy_server.sh`, `tools/remote_aloha/config.py`, `tools/remote_aloha/remote.py`, `.env.example`, `Makefile`, focused tests, and evidence references in plans/docs (raw output ignored).
- **Validation:** Direct-converter and JAX runtime defaults remain unchanged; focused local tests cover automatic/explicit conversion selection, explicit backend routing, rejection without a matching artifact, finite deadlines, locks, temporary ownership, both monolithic and sharded artifacts, sharded loading, and backend/device metadata; the PC proof checks representative BF16 value equivalence; partial conversion checks exact source/target counts, keys, shapes, dtypes, single writes, assets, shard index/hash, and fresh-model loading; profile-specific PyTorch smoke inference remains the final acceptance gate. Because WSL `nvidia-smi --query-compute-apps` did not expose the Torch server's Linux PID, PyTorch acceptance instead requires handshake proof that the loaded model itself is on `cuda:0`, 3090 sampling during inference, WSL host-RSS sampling, immediate owned-process verification, and survival in a second SSH session; JAX retains per-process `nvidia-smi` attribution.
- **Acceptance:** Both profiles allocate RTX 3090 memory and return valid actions; π₀.₅ task success is not inferred from shape validity; evidence is sanitized.
- **Planned commit:** `feat(remote): add bounded PyTorch recovery path`.
- **Actual findings:** JAX π₀ still OOMs and the stock whole-tree converter still exceeds current WSL RAM. The selected partial-BF16 experiment passed for both profiles. π₀ conversion peaked at 9,935,064 KiB RSS/21,256 MiB GPU; π₀.₅ peaked at 9,879,536 KiB RSS/21,979 MiB GPU. Final candidate `38b5228418c729d39d1c4fe551ef5ddcbef9e49e` returned four finite `(50,14)` actions per profile. π₀ cold/warmed latency was 1,639.0/291.8 ms with 1,907,312 KiB host RSS; experimental π₀.₅ was 1,331.1/335.6 ms with 1,943,684 KiB host RSS. Both models proved `cuda:0`/RTX 3090 placement, survived a second SSH session, and stopped safely. See E-PC-BF16.
- **Remaining blockers:** None within Phase 02. π₀.₅ remains an infrastructure/demo option, not a claim of simulator task quality. Mac-through-tunnel validation remains Phase 03.
